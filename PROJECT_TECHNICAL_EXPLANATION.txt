1. EXECUTIVE PROJECT OVERVIEW & CONTEXT
================================================================================
The GenAI Data Assistant is an enterprise-grade artificial intelligence platform designed to answer complex user questions across both unstructured text documents (e.g. employee handbooks, refund policies, SOPs) and structured relational databases (e.g. customer records, sales transactions, product inventories).

Key Design Objectives:
----------------------
1. Unified Natural Language Interface: Users submit plain English questions to a single POST /chat endpoint without needing to select a database or document search tool manually.
2. Intelligent Dynamic Routing: Uses a LangGraph StateGraph DAG to evaluate incoming user questions and automatically route execution to:
   - RAG Route ("rag"): Vector search over Qdrant for policy/document questions.
   - SQL Route ("sql"): Text-to-SQL generation and safe execution against PostgreSQL for database analytics.
   - Combined Route ("combined"): Parallel document retrieval + database query execution, synthesizing both data sources into a unified answer.
3. Strict Read-Only Security: Enforces AST (Abstract Syntax Tree) SQL validation using sqlglot, blocking non-SELECT queries (DROP, DELETE, UPDATE, INSERT, ALTER) prior to PostgreSQL execution.
4. Multi-Turn Session Memory: Thread-safe in-memory session tracking that auto-generates session IDs, maintains historical conversation turns, resolves pronouns in follow-up queries, and trims long histories to prevent context inflation.
5. Production Readiness: Clean monorepo separation, non-root Docker execution, 10 MB upload limits, health checks, OpenAPI Swagger metadata, and 100% green test suite (103 tests).

Why Monorepo Clean Architecture?
--------------------------------
Separating apps/api from packages/ ensures domain packages (rag, sql_agent, graph) have zero direct dependency on web framework code (FastAPI). This makes packages reusable in CLI tools, background workers, or alternative web delivery frameworks while ensuring high unit testability.

4. DEEP DIVE: DOCUMENT RAG PIPELINE
================================================================================
RAG (Retrieval-Augmented Generation) combines text search over custom document collections with generative LLM prompt synthesis.

Step-by-Step Flow:
------------------
1. File Upload & Ingestion:
   User posts document via POST /documents/ingest. DocumentService receives UploadFile.
   - Validates file extension (.pdf, .docx, .txt, .md).
   - Sanitizes filename using os.path.basename.
   - Validates file size (max 10 MB limit).
   - Saves file to data/documents/<uuid>_<filename>.

2. Document Parsing (packages/rag/ingest.py):
   DocumentParser checks file extension and delegates parsing:
   - .pdf -> PyPDFLoader
   - .docx -> Docx2txtLoader
   - .txt / .md -> TextLoader

3. Recursive Text Chunking (packages/rag/chunking.py):
   DocumentChunker uses RecursiveCharacterTextSplitter:
   - Chunk Size = 500 characters
   - Chunk Overlap = 100 characters
   Why Overlap? Overlapping adjacent chunks prevents sentences or key terms split across boundaries from losing context during semantic search.

4. Dense Vector Embedding Generation (packages/rag/embeddings.py):
   EmbeddingService generates dense vector representations using Google Gemini text-embedding-004 model (768 dimensions) in batches of 16 chunks (EMBEDDING_BATCH_SIZE=16).

5. Qdrant Vector Indexing (packages/rag/vector_store.py):
   QdrantVectorStore upserts point structs into Qdrant collection 'company_documents':
   - Vector: 768-float array
   - Metric: Cosine Distance
   - Payload Metadata: document_id, filename, file_type, page, chunk_index, text content.

6. Semantic Search & Citations (packages/rag/retriever.py):
   VectorRetriever converts query into vector embedding, executes Qdrant similarity search, filters results by RAG_SCORE_THRESHOLD (default: 0.5), and returns top RAG_TOP_K (default: 5) chunks. Source citation metadata (filename, page, chunk_index) is attached to the final ChatResponse.

5. DEEP DIVE: TEXT-TO-SQL AGENT & AST VALIDATION PIPELINE
================================================================================
The SQL Agent allows users to query relational database tables in plain English.

Step-by-Step Flow:
------------------
1. Dynamic Schema Introspection (packages/sql_agent/schema.py):
   SchemaInspectorService connects to PostgreSQL via SQLAlchemy inspection.
   Reflects table names, column names, column data types, primary keys, and foreign key relationships.
   Results are cached in memory using a thread-safe lock to eliminate database inspection overhead on subsequent calls.

2. Schema-Aware Text-to-SQL Prompting (packages/sql_agent/generator.py):
   SQLGeneratorService formats table schemas into prompt instructions:
   "Given the database schema: TABLE sales (id INT, customer_name VARCHAR, amount DECIMAL)... Convert question to SELECT query."
   Gemini generates clean PostgreSQL SELECT query statements.

3. Read-Only AST SQL Validation (packages/sql_agent/validator.py):
   Before reaching PostgreSQL, the raw generated SQL string is parsed into an Abstract Syntax Tree (AST) by sqlglot.parse_one(sql, read="postgres").
   Security Checks Enforced:
   - Statement Root: Must be Expression.Select or Expression.Expression (read-only CTE WITH statement).
   - Prohibited Statements: Rejects Expression.Delete, Expression.Insert, Expression.Update, Expression.Drop, Expression.Create, Expression.Alter, Expression.TruncateTable.
   - Single Statement Rule: Rejects semicolon-separated multi-statement strings.
   Why AST Validation? String pattern matching or regex bypasses easily via comments or aliasing. AST parsing guarantees mathematical structural safety at the syntax tree level.

4. Safe Execution Engine (packages/sql_agent/executor.py):
   SQLExecutorService executes validated SELECT queries against PostgreSQL via SQLAlchemy engine.
   - Row Limits: Output rows are capped at MAX_SQL_ROWS (default: 100) to prevent RAM exhaustion.
   - Metrics Logging: Records execution duration, query string, natural language question, and output row count.

6. DEEP DIVE: LANGGRAPH INTELLIGENT ROUTER & GRAPH NODES
================================================================================
LangGraph orchestrates agent execution as a stateful directed acyclic graph (DAG).

Graph State Definition (packages/graph/state.py):
-------------------------------------------------
AgentState is a TypedDict maintaining request workflow state:
- question / query: User input message string.
- intent / route: Classified route ("rag", "sql", or "combined").
- session_id: Active session memory identifier.
- conversation_history: Array of prior message dictionaries.
- retrieved_docs: Array of document chunks from vector search.
- sql_query / sql: Formulated SQL statement string.
- query_results: Output rows from database query execution.
- final_answer: Generated answer text.
- sources: Array of citation source metadata.

Graph Execution Nodes (packages/graph/nodes.py):
------------------------------------------------
1. Router Node (packages/graph/router.py -> route_intent_node):
   Calls Gemini with system classification instructions to categorize question into "rag", "sql", or "combined".
2. RAG Node (rag_node):
   Executes vector retrieval, formats retrieved text chunks into grounded prompt context, calls Gemini, and builds answer payload with document sources.
3. SQL Node (sql_node):
   Generates SQL, validates AST safety, executes query against PostgreSQL, and formats result rows into structured summary tables.
4. Combined Node (combined_node):
   Executes document vector search and PostgreSQL database query execution concurrently, passing both context blocks into Gemini to synthesize a single unified response.

Workflow DAG Assembly (packages/graph/workflow.py):
----------------------------------------------------
StateGraph(AgentState)
  -> Adds Nodes: "router", "rag", "sql", "combined"
  -> Sets Entry Point: "router"
  -> Adds Conditional Edges from "router" based on state["route"] to "rag", "sql", or "combined"
  -> Compiles graph_app instance.

7. DEEP DIVE: SESSION CONVERSATION MEMORY MANAGER
================================================================================
The ConversationMemoryManager (packages/graph/memory.py) handles session history and follow-up question continuation.

Core Components:
----------------
1. Session Data Model:
   - session_id: String identifier (e.g. custom or auto-generated hex).
   - history: Array of ConversationMessage objects (role="user" | "assistant", content, timestamp, route, sources, sql).
   - previous_route, previous_sources, previous_sql.

2. Thread Safety:
   Encapsulates session storage within threading.Lock() to prevent race conditions during concurrent API requests.

3. Memory Trimming:
   Caps conversation history at MAX_CONVERSATION_MESSAGES (default: 20 messages).
   When history exceeds 20 messages, the oldest interaction pairs drop automatically while preserving recent context turns.

4. Follow-Up Context Resolution:
   When a user sends a message with an existing session_id:
   - ChatService retrieves session history and passes history_dumps into LangGraph state.
   - LangGraph nodes prepend prior turns ("Context: user: ... | assistant: ...") into Gemini prompts.
   - Example Resolution:
     Turn 1: "Which customer spent the most?" -> Assistant: "Acme Corp ($150,000)".
     Turn 2: "What about second place?" -> Gemini uses history to resolve pronoun and generates query for 2nd highest spender ("Globex Corp").

10. SECURITY HARDENING & PERFORMANCE OPTIMIZATIONS
================================================================================

Security Measures Implemented:
------------------------------
1. AST SQL Protection: sqlglot parser enforces read-only SELECT queries, blocking SQL injection attempts and data modification operations.
2. File Upload Security:
   - Sanitizes filenames using os.path.basename to eliminate path traversal attacks (../).
   - Enforces a strict 10 MB file size limit check.
   - Restricts permitted extensions strictly to .pdf, .docx, .txt, .md.
3. Secret Isolation: Sensitive keys (GEMINI_API_KEY, DB passwords) are loaded strictly via Pydantic settings from environment variables.
4. Non-Root Container User: Docker app runs as unprivileged 'appuser' group/user.

Performance Optimizations Implemented:
--------------------------------------
1. Embedding Batching: Embeddings generated in batches of 16 (EMBEDDING_BATCH_SIZE=16) to minimize API roundtrips.
2. Thread-Safe Schema Caching: SchemaInspectorService caches database schema reflection in memory to avoid repeated database metadata queries.
3. Database Connection Pooling: SQLAlchemy engine configured with pool_size=5, max_overflow=10, and pool_pre_ping=True.
4. Memory Trimming: Caps conversation history size at MAX_CONVERSATION_MESSAGES=20 to prevent RAM memory inflation.

12. END-TO-END EXECUTION SCENARIOS (DATA FLOW)
================================================================================

Scenario A: Document Ingestion & RAG Question
--------------------------------------------
1. User calls POST /documents/ingest with file "employee_handbook.pdf".
2. DocumentService validates 10 MB size limit, saves file, parses text using PyPDFLoader, chunks text into 500-char pieces, generates 768-dim embeddings via text-embedding-004, and indexes vector points into Qdrant collection 'company_documents'.
3. User posts {"message": "What is the leave policy?"} to POST /chat.
4. ChatService loads session history, calls LangGraph DAG.
5. Router node classifies question as "rag".
6. rag_node queries Qdrant, retrieves handbook chunks, builds grounded prompt context, calls Gemini, and returns response with source citations.

Scenario B: Natural Language SQL Question
-----------------------------------------
1. User posts {"message": "Top 5 customers by revenue"} to POST /chat.
2. ChatService calls LangGraph DAG.
3. Router node classifies question as "sql".
4. sql_node inspects PostgreSQL schema, calls Gemini to generate SELECT SQL query, validates AST safety using sqlglot, executes SELECT query via SQLExecutorService, caps results at 100 rows, and formats result table.

Scenario C: Multi-Turn Conversation Memory Continuation
--------------------------------------------------------
1. Turn 1: User posts {"message": "Which product is most popular?"} to POST /chat.
   System returns answer and session_id "sess_abc123".
2. Turn 2: User posts {"message": "What is its price?", "session_id": "sess_abc123"} to POST /chat.
   ChatService fetches Turn 1 history from memory manager and injects prior turns into LangGraph state.
   Gemini uses history context to resolve "its" -> "Product A", generating SQL query for Product A's price.

13. INTERVIEW PREPARATION GUIDE (QUESTIONS & ANSWERS)
================================================================================

Q1: What is the main architectural advantage of using a Monorepo for this project?
Answer: A monorepo cleanly separates web API delivery (apps/api) from domain packages (packages/rag, packages/sql_agent, packages/graph). This prevents framework lock-in, allows domain logic to be reused across CLI tools or alternative web frameworks, and enables fast unit testing of core packages without spinning up HTTP servers.

Q2: How do you prevent malicious SQL injection or data deletion in your SQL Agent?
Answer: We implement AST (Abstract Syntax Tree) validation using sqlglot before execution. Rather than relying on fragile regex pattern matching, sqlglot parses the raw SQL string into an AST tree and verifies that the root statement is strictly an Expression.Select or read-only CTE. Any statement containing DROP, DELETE, UPDATE, INSERT, ALTER, or semicolon-separated multi-statements is blocked before reaching PostgreSQL.

Q3: How does your RAG pipeline ensure AI answers are grounded without hallucinations?
Answer: In rag_node, retrieved vector chunks from Qdrant are passed to Gemini within a strict anti-hallucination prompt envelope: "Answer the question using ONLY the provided document context below. If the answer cannot be found in the context, reply 'I couldn't find relevant information in the uploaded documents.'" Structured citations (filename, page, chunk_index) are attached to verify source provenance.

Q4: Why did you choose LangGraph StateGraph instead of standard LangChain chains?
Answer: Standard LangChain chains enforce simple sequential execution. Real-world AI data assistants require multi-branch state graphs capable of dynamic routing (RAG vs SQL vs Combined), parallel node execution, and explicit state schema management (AgentState). LangGraph provides stateful DAG workflow management with clean node separation.

Q5: How does your session memory handle memory growth over long conversations?
Answer: The ConversationMemoryManager includes an automatic memory trimming algorithm capped at MAX_CONVERSATION_MESSAGES (default: 20 messages). When session interaction turns exceed 20 messages, the oldest message pairs drop automatically while keeping recent context turns active, preventing context window inflation and RAM exhaustion.
